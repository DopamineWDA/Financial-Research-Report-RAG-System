## 分析

### 1. 整体趋势

从结果看，`chunk_size` 是影响切块形态的主因，`overlap` 的影响相对次要。

- 当 `chunk_size` 从 `256 -> 512 -> 1024` 增大时，`total_chunks` 明显下降，分别大致落在 `1.2w / 0.85w / 0.68w`，说明更大的块会显著减少索引条目数和召回候选数。
- 同时，`avg_tokens_per_chunk` 持续上升，约为 `283-308 / 383-392 / 462-467`，说明块更长、上下文更完整，但单块携带的无关信息也可能增加。
- `overlap` 从 `50 -> 100 -> 200` 时，所有 `chunk_size` 组的 `total_chunks` 都只是温和上升，说明 overlap 主要在补足上下文连续性，而不会像 `chunk_size` 那样改变整体切块密度。

### 2. 不同策略的取舍

- `256` 组最细，平均每篇文档约 `40-43` 个 chunk，适合提高定位精度，通常对短事实问答、细粒度召回更友好；代价是索引条目最多，召回结果更容易碎片化。
- `512` 组更均衡，平均每篇约 `28-29` 个 chunk，块长度明显提升，但总 chunk 数还没有压得太低，通常会是后续做 Recall@5 / 精确率综合权衡时最值得优先看的基线。
- `1024` 组最粗，平均每篇约 `22.5-22.7` 个 chunk，索引最紧凑，但文本块更长；如果问题只命中文档中的局部信息，可能会引入更多无关上下文。

如果只从切块统计出发、还没看 Recall@5，优先建议关注这三组：

- `256 / 50`：细粒度下的低重叠基线。
- `512 / 100`：相对均衡，最适合作为主对比基线。
- `1024 / 100`：大块策略代表，用来观察“更完整上下文”是否真的带来召回收益。

### 3. overlap 的具体影响

- 在同一 `chunk_size` 下，`overlap=200` 都会带来更多 chunk，例如 `512` 组从 `8406 -> 8477 -> 8760`，`1024` 组从 `6769 -> 6777 -> 6804`。
- 这种增长在 `256` 组更明显，说明小块本身边界更多，增大 overlap 后更容易产生额外切分。
- 因为 `avg_tokens_per_chunk` 也随 overlap 增大而上升，说明 overlap 不只是复制边界，还让更多 chunk 携带了前文信息；它可能对跨段落问题有帮助，但也可能压低去重后的有效信息密度。

### 4. 一个需要注意的统计信号

当前所有策略的 `max_tokens` 都固定为 `23892`。抽样检查后，这些超长 chunk 都来自 `raw_table_chunk`，而不是正文 `text_chunk`。这说明：

- 现阶段的 `chunk_size` 主要约束了文本块 `text_chunk`，但没有约束原始 HTML 表格块。
- 因此，表中的 `max_tokens` 不能直接理解为“该策略下文本 chunk 的最大长度”，它更像是在反映少量超长表格的存在。
- 这一点也会影响整体均值判断。比如 `1024` 组中，`table_related_chunks` 固定为 `3410`，占总 chunk 数已接近 `50%`；而 `256` 组中该比例约为 `28%`。这不是表格变多了，而是文本块变少后，表格块在总量中的占比被动上升。

补充看超长 chunk 统计，`token > 2000` 的 chunk 数在几组代表策略中都固定为 `125` 个：

- `256 / 50`：`125 / 12142`，约 `1.03%`
- `512 / 100`：`125 / 8477`，约 `1.47%`
- `1024 / 200`：`125 / 6804`，约 `1.84%`

也就是说，超长表格块的绝对数量没变，但在大块策略里它们占总 chunk 的比例更高。

### 5. 当前阶段的结论

只基于切块统计，不考虑召回实验结果的话：

- `256` 更偏向“细粒度覆盖”。
- `1024` 更偏向“少块长上下文”。
- `512` 是当前最均衡的一档。

后续如果要补 Recall@5，建议优先验证 `512 / 100` 能否在召回效果和索引规模之间形成最好平衡；如果 Recall@5 差距不大，优先选择 chunk 数更少的策略会更省存储和检索成本。
